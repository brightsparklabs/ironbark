== Overview

Ironbark is a CLI tool that bootstraps and manages Kubernetes clusters in air-gapped or disconnected environments using:

[horizontal]
https://zarf.dev/[Zarf]:: For packaging and deploying applications to air-gapped Kubernetes clusters.
https://argo-cd.readthedocs.io/[ArgoCD]:: For GitOps-based continuous deployment.
https://argo-cd.readthedocs.io/en/latest/operator-manual/cluster-bootstrapping/#app-of-apps-pattern-alternative[App of Apps Pattern]:: For managing multiple applications declaratively.

Ironbark automates the setup of a complete GitOps workflow in disconnected environments by:

. Deploying core infrastructure components (ArgoCD, External Secrets Operator, etc.).
. Setting up internal Git and OCI registry access.
. Configuring ArgoCD to sync applications from internal repositories.
. Providing a structured way to manage application deployments.

=== Key Features

[horizontal]
Air-gapped deployment:: Works in completely disconnected environments.
Zarf integration:: Packages all dependencies for offline installation.
GitOps ready:: Automated ArgoCD setup with App of Apps pattern.
Secure by default:: Automated secret management and TLS proxy configuration.
Opinionated workflow:: Standardised deployment patterns across teams.

Ironbark manages several key components:

│  └────────────┘    └──────────────┘   └──────────────┘  │
│        │                                      ^         │
│        │ Syncs Apps                           │         │
│        v                                      │         │

│  │  App of Apps Repo (ironbark-argocd-app-of-apps)   │  │

│  │  └── values/               (App configurations)   │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
│  Deployed Applications:                                 │
│  ├── External Secrets Operator                          │

└─────────────────────────────────────────────────────────┘
----

=== Components

[horizontal]
bsl-ironbark:: Core package containing ArgoCD, External Secrets Operator, and utilities.
App of Apps Repo:: Git repository containing Helm charts and values for all applications.
Internal TLS Proxy:: Caddy-based proxy for HTTPS access to internal HTTP services.
Zarf Secrets Sync:: Ensures Zarf registry/repo credentials are available in all namespaces.

== Installation

=== Prerequisites

* Kubernetes cluster (K3s, etc.).
* `kubectl` configured and connected to your cluster.
* Zarf already initialised on the cluster (`zarf init`).

=== Procedure

Generate a launcher script using the Ironbark container.
The launcher wraps the underlying container engine invocation so you can run `ironbark` directly:

[source,bash]
----
# Pre-create the canonical Ironbark install root and hand ownership to the
# current user so subsequent `ironbark` invocations do not require `sudo`.
sudo mkdir -p /opt/brightsparklabs/ironbark/{bin,data}
sudo chown -R "$(id -u):$(id -g)" /opt/brightsparklabs/ironbark

# Generate a launcher script (defaults to Podman) and install it onto your
# $PATH at the canonical location. The default `--data-dir` already points
# at `/opt/brightsparklabs/ironbark/data` so no flag is required.
podman run --rm brightsparklabs/ironbark generate launcher \
  > /opt/brightsparklabs/ironbark/bin/ironbark
chmod +x /opt/brightsparklabs/ironbark/bin/ironbark

# Make sure the launcher is on your PATH for the rest of this guide. Add this
# line to your shell profile (e.g. `~/.bashrc`, `~/.zshrc`) to make it
# permanent.
export PATH="/opt/brightsparklabs/ironbark/bin:${PATH}"
----

Available options for `ironbark generate launcher`:

[horizontal]
`--container-engine`:: Container engine to use (`podman` or `docker`). Default: `podman`.
`--image`:: Container image reference for Ironbark. Default: `brightsparklabs/ironbark:latest`.
`--data-dir`:: Host directory mounted into the container as the Ironbark data directory. Default: `/opt/brightsparklabs/ironbark/data` (the canonical install location).
`--kubeconfig`:: Host kubeconfig file mounted into the container. Default: `${HOME}/.kube/config`.
`--no-interactive`:: Bake `IRONBARK_SCRIPT_NO_INTERACTIVE` on as the default in the generated script (useful for CI). Default: `false`.
`--no-tty`:: Bake `IRONBARK_SCRIPT_NO_TTY` on as the default in the generated script (useful when piping or in CI). Default: `false`.

The generated script:

* Attempts to create the host data directory if it does not exist.
If the creation fails (e.g. permission denied) the script reports the error and exits with a non-zero status.
* Relies on `IRONBARK_IN_CONTAINER=true` being baked into the Ironbark image so code (and shell scripts) can detect that they are running inside the container, regardless of whether the launcher or a direct `podman run` was used.
* Forwards a number of useful host details into the container as `IRONBARK_HOST_*` environment variables so that Ironbark can correctly reference paths and identities on the host (e.g. when invoking nested container engines):
+
[horizontal]
`IRONBARK_HOST_USER`:: Effective host user (`${SUDO_USER:-$USER}`).
`IRONBARK_HOST_UID`:: Effective host user id (`${SUDO_UID:-$(id -u)}`).
`IRONBARK_HOST_GID`:: Effective host group id (`${SUDO_GID:-$(id -g)}`).
`IRONBARK_HOST_HOSTNAME`:: Hostname of the invoking machine.
`IRONBARK_HOST_PWD`:: Working directory the launcher was invoked from.
`IRONBARK_HOST_OS`:: Host operating system (`uname -s`).
`IRONBARK_HOST_ARCH`:: Host CPU architecture (`uname -m`).
`IRONBARK_HOST_DATA_DIR`:: Host path of the mounted data directory.
`IRONBARK_HOST_KUBECONFIG`:: Host path of the mounted kubeconfig file.
`IRONBARK_HOST_CONTAINER_ENGINE`:: Container engine used to run Ironbark (`podman` or `docker`).
`IRONBARK_HOST_LAUNCHER_VERSION`:: Version of the Ironbark binary that generated the launcher script.
`IRONBARK_HOST_LAUNCHER_COMMIT`:: Short Git commit hash of the Ironbark binary that generated the launcher script.
`IRONBARK_HOST_LAUNCHER_BUILD_TIME`:: UTC ISO 8601 timestamp recording when the Ironbark binary that generated the launcher script was built.
`IRONBARK_HOST_LAUNCHER_GENERATED_AT`:: Timestamp recording when the launcher script itself was generated.
* Honours `IRONBARK_SCRIPT_NO_INTERACTIVE` and `IRONBARK_SCRIPT_NO_TTY` at runtime: define either variable to ANY value (e.g. `true`, `1`, `yes`) to disable `--interactive` / `--tty` without regenerating the script.
Leave them unset to keep the flags enabled.
* Honours `IRONBARK_SCRIPT_VERBOSE`: define it to ANY value to print the resolved settings (container engine, image, mounts, flag state, forwarded host env vars) to stderr before invoking the container engine.

To generate a launcher targeting Docker instead of Podman (substitute `podman` for `docker` in the bootstrap command from the previous example):

[source,bash]
----
docker run --rm brightsparklabs/ironbark generate launcher \
  --container-engine docker \
  > /opt/brightsparklabs/ironbark/bin/ironbark
chmod +x /opt/brightsparklabs/ironbark/bin/ironbark
----

=== Bootstrapping a Host with Zarf

When bootstrapping a fresh host (e.g. installing K3s via `zarf init`) you need the `zarf` CLI and the `zarf-init-*.tar.zst` package on the host itself.
The Ironbark container ships both at `/app/resources/zarf/init`.
Rather than manually invoking `podman cp ...`, generate a host-side extraction script.

This is only required when the target host does not already have a Kubernetes cluster available; if a cluster already exists, Ironbark can talk to it directly via its kubeconfig and you can skip this step entirely.

Before emitting the script, `generate zarf-bootstrap` verifies that the Zarf assets (the `zarf` CLI and a matching `zarf-init-*.tar.zst` package) actually exist at the configured source path.
This catches misconfigurations such as a stale image or a wrong `--source-path` early, instead of letting the operator discover the problem after running the resulting script on the host.

[source,bash]
----
# Generate the extraction script using the launcher installed above and run
# it on the host.
ironbark generate zarf-bootstrap > extract-zarf.sh
chmod +x extract-zarf.sh
./extract-zarf.sh

# Bootstrap the host (installs K3s and the Zarf in-cluster components).
# `zarf init` is interactive; the operator is prompted to confirm.
cd /opt/brightsparklabs/ironbark/data/zarf/init
sudo ./zarf init
----

Available options for `ironbark generate zarf-bootstrap`:

[horizontal]
`--container-engine`, `-e`:: Container engine to use (`podman` or `docker`). Default: `podman`.
`--image`, `-i`:: Container image reference for Ironbark. Default: `brightsparklabs/ironbark:latest`.
`--source-path`, `-s`:: Path inside the container containing the Zarf CLI and init package. Default: `/app/resources/zarf/init`.
`--output-dir`, `-o`:: Host directory which will receive the extracted Zarf assets. Default: `/opt/brightsparklabs/ironbark/data/zarf/init` (sits inside the launcher's default data directory so no extra mount is required).

The generated script:

* Validates that the requested container engine is available on `PATH`.
* Creates the output directory if it does not already exist.
* Creates a throwaway Ironbark container, copies the Zarf assets out, then removes the throwaway container (always, via a `trap`).
* Honours runtime overrides via `IRONBARK_SCRIPT_CONTAINER_ENGINE`, `IRONBARK_SCRIPT_IMAGE`, `IRONBARK_SCRIPT_ZARF_SOURCE_PATH`, `IRONBARK_SCRIPT_ZARF_OUTPUT_DIR`, and `IRONBARK_SCRIPT_VERBOSE`, so you can change the defaults without regenerating the script.
* Does NOT run `zarf init` itself; the operator retains explicit control over the bootstrap step.

=== Generating fapolicyd Rules

Hosts that enforce `fapolicyd` need explicit rules to allow execution of the binaries Ironbark relies on (the extracted `zarf` CLI and the installed `k3s` CLI).
Generate a matching rules file with:

[source,bash]
----
# Defaults assume `/opt/brightsparklabs/ironbark/data/zarf/init/zarf` and
# `/usr/local/bin/k3s`.
ironbark generate fapolicy-rules \
  --zarf-path /opt/brightsparklabs/ironbark/data/zarf/init/zarf \
  --k3s-path /usr/local/bin/k3s \
  | sudo tee /etc/fapolicyd/rules.d/30-ironbark.rules > /dev/null
sudo systemctl restart fapolicyd
----

Available options for `ironbark generate fapolicy-rules`:

[horizontal]
`--zarf-path`:: Absolute host path of the extracted Zarf CLI. Default: `/opt/brightsparklabs/ironbark/data/zarf/init/zarf` (matches the default `--output-dir` of `generate zarf-bootstrap`).
`--k3s-path`:: Absolute host path of the installed K3s CLI. Default: `/usr/local/bin/k3s`.

The generated rules file allows execution and reading of each supplied binary.

== Usage

=== Quick Start

To set up a complete Ironbark deployment:

[source,bash]
----
# Initialise all Ironbark components.
ironbark init all
----

This command will:

. Deploy Ironbark packages (ArgoCD, External Secrets Operator, etc.).
. Mirror required container images to the Zarf registry.
. Create ArgoCD repository secrets for accessing Zarf Git and OCI registry.
. Initialise the ArgoCD App of Apps repository.
. Deploy the ArgoCD App of Apps to start syncing applications.

=== Step-by-Step Initialisation

You can also run individual initialisation steps:

[source,bash]
----
# 1. Deploy and mirror Ironbark packages.
ironbark init packages

# 2. Set up ArgoCD repository secrets.
ironbark init argocd-repo-secrets

# 3. Create and push the App of Apps repository.
ironbark init argocd-app-of-apps-repo

# 4. Deploy the ArgoCD App of Apps.
ironbark init argocd-app
----

=== Managing Applications

After initialisation, manage your applications by:

. Edit the App of Apps repository locally:
+
[source,bash]
----
cd "${IRONBARK_HOST_DATA_DIR}/repos/ironbark-argocd-app-of-apps"

# Add applications to chart/values.yaml.
# Add value files to values/<app-name>/.
----

. Push changes to the internal Git server:
+
[source,bash]
----
ironbark argo push
----

. ArgoCD will automatically sync the changes and deploy your applications.

=== Accessing ArgoCD

[source,bash]
----
# Get ArgoCD admin password.
kubectl get secret -n bsl-ironbark-argocd \
  argocd-initial-admin-secret -o jsonpath='{.data.password}' \
  | base64 -d

# Port forward to ArgoCD UI.
kubectl port-forward -n bsl-ironbark-argocd services/argocd-server 8443:443

# Open https://localhost:8443 in your browser.
# Username: admin.
# Password: (from command above).
----

=== Accessing Zarf Git Server

[source,bash]
----
# Connect to Git server.
zarf connect git --local-port 5002

# Get credentials.
zarf tools get-creds git

# Access at http://localhost:5002.
----

== Diagnostic Commands

Ironbark groups its troubleshooting subcommands under `ironbark debug`.
These commands never modify any external system; they only read and print information that Ironbark already has access to.

=== Inspecting Settings

`ironbark debug settings` prints the full catalogue of `IRONBARK_*` environment variables Ironbark knows about, along with each variable's current effective value, declared default, source (env or default), scope, and a short description.

[source,bash]
----
# Default human-readable table.
ironbark debug settings

# Machine-readable output for piping into other tools.
ironbark debug settings --format json
ironbark debug settings --format yaml
----

The catalogue in `src/internal/settings/settings.go` is the single source of truth for every `IRONBARK_*` variable understood by the system.
The unit tests for that package enforce that variable names are unique, well-formed (`IRONBARK_*` prefix), and that every Go-consumed accessor has a matching catalogue entry, so the output of `debug settings` cannot drift from the real list of variables Ironbark reads.

Variables marked sensitive (currently none) are rendered with their values redacted as `<redacted>` regardless of the chosen output format.

== Adding New Applications

To add a new application to your Ironbark deployment:

. Ensure the Helm chart is mirrored to the Zarf OCI registry (via a Zarf package).

. Edit the App of Apps configuration:
+
[source,bash]
----
cd "${IRONBARK_HOST_DATA_DIR}/repos/ironbark-argocd-app-of-apps"
----

. Add the application to `chart/values.yaml`:
+
[source,yaml]
----
applications:
  - name: my-app
    chart:
      name: repository/chart-name
      targetRevision: 1.0.0
    values:
      path: values/my-app/values.yaml
      targetRevision: HEAD
      # Optional: Set Helm values from file contents (equivalent to `helm --set-file`).
      fileParameters:
        # Equivalent to `helm --set-file config.json=values/my-app/config.json`.
        - name: config.json
          path: values/my-app/config.json
        # Equivalent to `helm --set-file tls.cert=values/my-app/cert.pem`.
        - name: tls.cert
          path: values/my-app/cert.pem
----

. Create values file at `values/my-app/values.yaml`:
+
[source,yaml]
----
# Your Helm values here.
replicaCount: 2
----

. Commit and push changes:
+
[source,bash]
----
git add .
git commit -m "Add my-app"
ironbark argo push
----

. ArgoCD will automatically deploy the application.

----
# Clone the repository.
git clone https://github.com/brightsparklabs/ironbark.git

== Troubleshooting

=== ArgoCD Applications Not Syncing

[source,bash]
----
# Check ArgoCD application status.
kubectl get applications -n bsl-ironbark-argocd

# View ArgoCD logs.
kubectl logs -n bsl-ironbark-argocd -l app.kubernetes.io/name=argocd-server

# Check repo server logs for Git/OCI issues.
kubectl logs -n bsl-ironbark-argocd -l app.kubernetes.io/name=argocd-repo-server
----

=== Cannot Push to Git Repository

[source,bash]
----
# Verify Git tunnel is working.
zarf connect git --local-port 5002

# Check credentials.
zarf tools get-creds git

# Verify the repository exists in Gitea.
# Access Gitea UI at http://localhost:5002.
----

=== OCI Registry Connection Issues

The internal TLS proxy provides HTTPS access to the Zarf OCI registry:

[source,bash]
----
# Check TLS proxy status.
kubectl get pods -n bsl-ironbark-internal-tls-proxy

# View proxy logs.
kubectl logs -n bsl-ironbark-internal-tls-proxy -l app=internal-tls-proxy
----
