= Ironbark
:toc: left
:sectnums:

Ironbark is a Kubernetes deployment tool designed for air-gapped environments.
It simplifies the deployment and management of applications through a self-hosted ArgoCD App of Apps repository pattern.

== Compatibility

[cols="3,2,3"]
|===
|Ironbark Version |Zarf Version |RKE2 Version (RKE2 variant only)

|0.x.y |0.64.0 |v1.33.5+rke2r1
|===

== Overview

Ironbark provides an API-first approach to deploying and managing Kubernetes applications in air-gapped or disconnected environments.
It is designed to work with existing Kubernetes clusters or can perform a complete air-gapped deployment of a new cluster using RKE2 (preferred) or K3s.

The tool makes it easy to manage application deployments through a self-hosted ArgoCD App of Apps repository pattern, providing:

Air-gapped deployment:: Deploys required artifacts (container images, Helm charts, binaries) without requiring internet access on the target environment.
GitOps workflow:: Uses ArgoCD with an App of Apps pattern for declarative application management.
Self-hosted Git server:: Internal Gitea instance for repository hosting in disconnected environments.
Multiple Kubernetes distributions:: Supports deploying either RKE2 or K3s (via Zarf) for cluster bootstrapping.
Artifact management:: Download RKE2 installation files, zarf-init packages, and other resources via HTTP endpoints.

Ironbark runs as a container and exposes:

[horizontal]
Port 8080:: REST API for cluster management, repository operations, and configuration.
Port 3000:: Git HTTP proxy for cloning/pushing to the internal Gitea server.

== Quick Start

This quick start assumes you have an existing Kubernetes cluster.
If you need to install Kubernetes in an air-gapped environment, see <<Air-gapped Kubernetes Installation>>.

=== Prerequisites

* A Kubernetes cluster (EKS, RKE2, K3s, GKE, etc.)
* Access to the cluster's kubeconfig file
* Container runtime (Podman or Docker)

=== Start Ironbark

[source,bash]
----
# Start Ironbark in API server mode.
podman run -d \
  --name ironbark \
  --port 8080:8080 \
  --port 3000:3000 \
  docker.io/brightsparklabs/ironbark:latest
----

[IMPORTANT]
The above requires that your kubeconfig to use the cluster's external IP address.
If your kubeconfig connects to `localhost` or `127.0.0.1` (i.e. a local cluster on host), then use `--network host`.
This allows the container to access the cluster.

=== Upload Kubeconfig

Upload your cluster's kubeconfig to Ironbark:

[source,bash]
----
curl -X POST http://localhost:8080/ironbark/api/v1/k8s/kubeconfig \
  --data-binary @~/.kube/config
----

=== Initialise Ironbark

Run the smart initialisation endpoint to set up all components:

[source,bash]
----
curl -X POST http://localhost:8080/ironbark/api/v1/init
----

This will:

. Initialise Zarf with the git-server component (if not already present).
. Deploy Ironbark packages (ArgoCD, External Secrets Operator, etc.).
. Create ArgoCD repository secrets for accessing the Zarf Git and OCI registry.
. Create and push the ArgoCD App of Apps repository.
. Deploy the ArgoCD Application to start syncing.

=== Clone the App of Apps Repository

Once initialisation is complete, clone the repository to manage your applications:

[source,bash]
----
git clone http://localhost:3000/zarf-git-user/ironbark-argocd-app-of-apps.git
cd ironbark-argocd-app-of-apps
----

You can now add applications by editing the repository and pushing changes back through the Git proxy.

== Usage

Ironbark operates primarily through its REST API.
All cluster management, repository operations, and configuration are performed via HTTP endpoints.

=== Health & Diagnostics

Check API server health:

[source,bash]
----
curl http://localhost:8080/ironbark/api/v1/health
# Response: {"status":"healthy"}
----

Get version information:

[source,bash]
----
curl http://localhost:8080/ironbark/api/v1/version
# Response: {"version":"v0.0.2","commit":"abc1234","buildTime":"2026-07-15T00:00:00Z"}
----

View configuration settings:

[source,bash]
----
curl http://localhost:8080/ironbark/api/v1/debug/settings
# Response: Array of configuration values with sources
----

=== Kubeconfig Management

Upload a kubeconfig:

[source,bash]
----
curl -X POST http://localhost:8080/ironbark/api/v1/k8s/kubeconfig \
  --data-binary @~/.kube/config
----

Retrieve the active kubeconfig:

[source,bash]
----
curl http://localhost:8080/ironbark/api/v1/k8s/kubeconfig
----

Delete the uploaded kubeconfig (reverts to mounted kubeconfig):

[source,bash]

curl -X DELETE http://localhost:8080/ironbark/api/v1/k8s/kubeconfig
----

List repositories in the internal Git server:

[source,bash]
----

# Response: {"repositories":[{"name":"ironbark-argocd-app-of-apps",...}],"count":1}
----

=== Initialisation Operations

Initialise all components (idempotent, auto-detects completed steps):

[source,bash]
----
curl -X POST http://localhost:8080/ironbark/api/v1/init
----

Initialise specific components:

[source,bash]
----
# Initialise only Zarf with git-server.
curl -X POST http://localhost:8080/ironbark/api/v1/init/zarf

# Deploy Ironbark packages.
curl -X POST http://localhost:8080/ironbark/api/v1/init/packages

# Set up ArgoCD repository secrets.
curl -X POST http://localhost:8080/ironbark/api/v1/init/argocd-repo-secrets

# Create and push the App of Apps repository.
curl -X POST http://localhost:8080/ironbark/api/v1/init/argocd-app-of-apps-repo

# Deploy the ArgoCD Application.
curl -X POST http://localhost:8080/ironbark/api/v1/init/argocd-app
----

=== Artifact Downloads

Download embedded artifacts from the container:

[source,bash]
----
# List available artifacts.
curl http://localhost:8080/ironbark/api/v1/artifact

# Download RKE2 artifacts (only in ironbark-rke2 variant).
curl -o rke2.tar.gz http://localhost:8080/ironbark/api/v1/artifact/rke2

# Download zarf-init package.
curl -O http://localhost:8080/ironbark/api/v1/artifact/zarf-init
----

Available artifacts:

[horizontal]
rke2:: RKE2 installation artifacts (only in `ironbark-rke2` container variant).
zarf-init:: Zarf init package for bootstrapping K3s clusters.

== Adding New Applications

To add a new application to your Ironbark deployment:

. Ensure the Helm chart is mirrored to the Zarf OCI registry (via a Zarf package).
+
Any chart declared under `components[].charts` in a mirror package is pushed to the in-cluster OCI registry automatically when `ironbark init packages` runs.
The chart lands at a predictable path that preserves upstream provenance:
+
URL-sourced charts (`oci://` or `https://`):: `oci://<zarf-registry>/ironbark/charts/<upstream-host-and-path>/<chart-name>:<chart-version>`.
+
E.g.
+
A chart declared as:::
+
----
url: oci://ghcr.io/cowboysysop/charts/whoami (version `6.0.0`)
----
Lands at:::
+
----
oci://<zarf-registry>/ironbark/charts/ghcr.io/cowboysysop/charts/whoami:6.0.0
----
Local charts (`localPath`, `gitPath`):: `oci://<zarf-registry>/ironbark/charts/<zarf-package-name>/<chart-name>:<chart-version>`.
+
The Zarf package name is used as the namespace because no upstream URL is available; this prevents collisions when two packages ship a chart with the same name.
+
All four Zarf chart source types are supported (`localPath`, `gitPath`, `url: https://`, `url: oci://`).
Use the predictable path to reference the mirrored chart from your ArgoCD `Application` (or any other in-cluster consumer).
+
[NOTE]
.Umbrella (chart-of-charts) support
--
Umbrella charts work without any special configuration.
`zarf package create` vendors all `Chart.yaml` dependencies into the parent chart's `charts/` directory at package-build time, so by the time the chart reaches Ironbark's mirror step it is a self-contained archive.
Only the umbrella chart itself is pushed to the in-cluster registry; sub-charts ride along inside it and Helm resolves them locally at install time.

Caveat: container images referenced from sub-chart templates or hooks are not always auto-detected by Zarf's image discovery pass.
If a sub-chart fails to deploy because an image was not mirrored, add the missing image to the parent component's `images:` list in `zarf.yaml`.
--
+
[NOTE]
--
This works around an upstream Zarf limitation where `zarf package mirror-resources` only mirrors images and Git repos, never Helm charts.
The chart-mirror step is implemented in Ironbark itself; see `internal/zarf/charts.go`.
--

. Clone the App of Apps repository:
+
[source,bash]
----
git clone http://localhost:3000/zarf-git-user/ironbark-argocd-app-of-apps.git
cd ironbark-argocd-app-of-apps
----

. Add the application to `chart/values.yaml`:
+
The `chart.name` must be the chart path mirrored by Ironbark, without the `oci://<zarf-registry>/` prefix (ArgoCD prepends the registry host from the repo secret).
+
For example, the canary chart at::
+
----
oci://<zarf-registry>/ironbark/charts/ghcr.io/cowboysysop/charts/whoami:6.0.0
----
+
Is referenced as::
+
[source,yaml]
----
applications:
  - name: whoami
    chart:
      name: ironbark/charts/ghcr.io/cowboysysop/charts/whoami
      targetRevision: 6.0.0
    values:
      path: values/whoami/values.yaml
      targetRevision: HEAD
      # Optional: Set Helm values from file contents (equivalent to `helm --set-file`).
      fileParameters:
        # Equivalent to `helm --set-file config.json=values/whoami/config.json`.
        - name: config.json
          path: values/whoami/config.json
        # Equivalent to `helm --set-file tls.cert=values/whoami/cert.pem`.
        - name: tls.cert
          path: values/whoami/cert.pem
----

. Create values file at `values/whoami/values.yaml`:
+
[source,yaml]
----
# Your Helm values here.
replicaCount: 2
----

. Commit and push changes:
+
[source,bash]
----
git add .
git commit -m "Add whoami"
git push origin main
----

. ArgoCD will automatically deploy the application.

== Troubleshooting

=== Container Won't Start

*Problem:* Container exits immediately or won't start.

*Solution:* Check container logs:

[source,bash]
----
podman logs ironbark
----

Common issues:

* Port 8080 or 3000 already in use - change port mapping.
* Permission issues - ensure podman has necessary privileges.

=== Init Endpoint Fails

*Problem:* `POST /init` returns an error.

*Solution:* Check prerequisites:

[source,bash]
----
# Verify kubeconfig is uploaded and accessible.
curl http://localhost:8080/ironbark/api/v1/k8s/kubeconfig

# Check container logs for detailed error messages.
podman logs ironbark
----

Common causes:

* No kubeconfig uploaded or mounted.
* Kubeconfig points to localhost but container not using `--network host`.
* Cluster is not accessible from container.

=== Git Clone Fails

*Problem:* Cannot clone repository through Git proxy.

*Solution:* Ensure Zarf is initialised:

[source,bash]
----
# Check if git-server is running.
kubectl get pods -n zarf

# Verify init was successful.
curl -X POST http://localhost:8080/ironbark/api/v1/init/zarf
----

=== Applications Not Deploying

*Problem:* ArgoCD not syncing applications.

*Solution:* Check ArgoCD status:

[source,bash]
----
# Check ArgoCD pods.
kubectl get pods -n bsl-ironbark-argocd

# Check Application status.
kubectl get applications -n bsl-ironbark-argocd
----

== Development

=== Architecture

Ironbark follows a layered architecture:

*Container Layer:* 

* Runs as HTTP API server by default (port 8080).
* Git HTTP proxy for repository access (port 3000).
* Embedded artifacts (zarf-init, RKE2 binaries).

*API Layer:*

* REST endpoints for all operations.
* Smart initialisation with idempotent operations.
* Kubeconfig management (upload, retrieve, delete).
* Artifact downloads for air-gapped deployment.

*Integration Layer:*

* Zarf integration for K3s bootstrapping and package management.
* Gitea for internal Git repository hosting.
* ArgoCD for GitOps-based application deployment.

*Storage Layer:*

* Zarf OCI registry for container images.
* Gitea for Git repositories.
* Internal state managed by Zarf cluster CRDs.

== Air-gapped Kubernetes Installation

This section covers installing Kubernetes in an air-gapped environment using artifacts downloaded from Ironbark.

=== Using RKE2 (Recommended)

RKE2 is Rancher's security-focused Kubernetes distribution, ideal for air-gapped and compliance-driven environments.

==== Install RKE2

. Start the Ironbark RKE2 container:
+
[source,bash]
----
podman run -d \
  --name ironbark \
  --network host \
  docker.io/brightsparklabs/ironbark-rke2:latest
----

. Download and extract RKE2 artifacts:
+
[source,bash]
----
mkdir -p ~/rke2-setup
cd ~/rke2-setup
curl -o rke2.tar.gz http://localhost:8080/ironbark/api/v1/artifact/rke2
tar -xzf rke2.tar.gz
cd rke2/resources/rke2
----

. Configure RKE2 to use Cilium CNI:
+
[source,bash]
----
sudo mkdir -p /etc/rancher/rke2
sudo cp config.yaml.template /etc/rancher/rke2/config.yaml
----

. Install RKE2 from local artifacts (air-gapped):
+
[source,bash]
----
sudo INSTALL_RKE2_TYPE=server \
  INSTALL_RKE2_ARTIFACT_PATH=$(pwd) \
  sh install.sh
----

. Copy container image tarballs to RKE2:
+
[source,bash]
----
sudo mkdir -p /var/lib/rancher/rke2/agent/images
sudo cp rke2-images-*.tar.zst /var/lib/rancher/rke2/agent/images/
----
+
IMPORTANT: Both `rke2-images-cilium` and `rke2-images-core` tarballs are required for air-gapped deployment.

. Start RKE2:
+
[source,bash]
----
sudo systemctl enable rke2-server.service
sudo systemctl start rke2-server.service
----

. Set up kubectl access:
+
[source,bash]
----
mkdir -p ~/.kube
sudo cp /etc/rancher/rke2/rke2.yaml ~/.kube/config
sudo chown $(id -u):$(id -g) ~/.kube/config
export PATH=$PATH:/var/lib/rancher/rke2/bin
----

==== Initialise Cluster

. Verify cluster is operational:
+
[source,bash]
----
kubectl get nodes
kubectl get pods -A
----

. Upload kubeconfig to Ironbark:
+
[source,bash]
----
curl -X POST http://localhost:8080/ironbark/api/v1/k8s/kubeconfig \
  --data-binary @/etc/rancher/rke2/rke2.yaml
----

. Initialise Ironbark components:
+
[source,bash]
----
curl -X POST http://localhost:8080/ironbark/api/v1/init
----

=== Using K3s (Alternative)

For K3s deployment, use the default Ironbark image with zarf-init:

. Download zarf-init package:
+
[source,bash]
----
curl -O http://localhost:8080/ironbark/api/v1/artifact/zarf-init
----

. Run zarf init:
+
[source,bash]
----
zarf init --components=git-server --confirm zarf-init-amd64-*.tar.zst
----

. Continue with <<Initialise Cluster>> from the RKE2 workflow above.

== Usage via CLI

For advanced use cases or direct host execution, Ironbark provides CLI commands through a launcher script workflow.

=== Prerequisites

. The environment has a working Kubernetes cluster (EKS, RKE2, K3s, etc.).
. `kubectl` is configured and connected to the cluster.
. Zarf has been initialised on the cluster (`zarf init`).

If any of the above are not met, refer to <<Air-gapped Kubernetes Installation>>.

=== Shell Environment

Set these environment variables before installation:

[source,bash]
----
# Base directory for Ironbark installations.
export IRONBARK_INSTALL_BASE_DIR="/opt/brightsparklabs/ironbark"

# Release environment (e.g., production, staging).
export IRONBARK_RELEASE_ENVIRONMENT="production"

# Per-environment install directory (derived from above).
export IRONBARK_INSTALL_DIR="${IRONBARK_INSTALL_BASE_DIR}/${IRONBARK_RELEASE_ENVIRONMENT}"
----

=== Easy Install (Recommended)

Use `generate installer` to create a self-contained bash installer:

[source,bash]
----
# Set the Ironbark image version.
export IRONBARK_SCRIPT_IMAGE=docker.io/brightsparklabs/ironbark:latest

# Generate and run the installer.
podman run --rm ${IRONBARK_SCRIPT_IMAGE} generate installer \
    --install-base-dir "${IRONBARK_INSTALL_BASE_DIR}" \
    --release-environment "${IRONBARK_RELEASE_ENVIRONMENT}" \
  | sudo bash

# Add the launcher to your PATH.
export PATH="${IRONBARK_INSTALL_DIR}/bin:${PATH}"
----

The installer:

. Creates the install directory tree under `/opt/brightsparklabs/ironbark/<environment>/`.
. Generates a versioned launcher script in `bin/`.
. Creates a generic `bin/ironbark` symlink.
. Sets proper ownership and permissions.

Available options for `ironbark generate installer`:

[horizontal]
`--install-base-dir`:: Base directory for installations. Default: `/opt/brightsparklabs/ironbark`.
`--release-environment`:: Target environment. Default: `production`.

All flags from `generate launcher` are also supported.

=== Manual Install (Alternative)

Generate a launcher script manually:

[source,bash]
----
# Generate the launcher script.
podman run --rm ${IRONBARK_SCRIPT_IMAGE} generate launcher \
  > "${IRONBARK_INSTALL_DIR}/bin/ironbark"

chmod +x "${IRONBARK_INSTALL_DIR}/bin/ironbark"

# Add to PATH.
export PATH="${IRONBARK_INSTALL_DIR}/bin:${PATH}"
----

Available options for `ironbark generate launcher`:

[horizontal]
`--container-engine`, `-e`:: Container engine (`podman` or `docker`). Default: `podman`.
`--image`, `-i`:: Ironbark container image reference. Default: `docker.io/brightsparklabs/ironbark:latest`.
`--kubeconfig`, `-k`:: Path to kubeconfig file on host. Default: `~/.kube/config`.
`--no-interactive`:: Disable interactive mode (pass `-i` to container engine).
`--no-tty`:: Disable TTY allocation (pass `-t` to container engine).

=== Configuration Environment Variables

All `IRONBARK_*` environment variables are defined and documented in `internal/settings/settings.go`.
The complete catalogue can be viewed at runtime using `ironbark debug settings`.

==== Go-Consumed Variables

These variables are read directly by the Ironbark binary:

[horizontal]
`IRONBARK_DATA_DIR`:: Directory used by Ironbark to store application data (cloned repos, etc.). Default: `/tmp/ironbark/data`.
`IRONBARK_INTERNAL_PACKAGES_DIR`:: Directory containing the internal Zarf packages bundled with Ironbark. Default: `/tmp/ironbark/packages`.
`IRONBARK_LOG_LEVEL`:: Minimum log level for the Ironbark binary (debug, info, warn, error). Default: `info`.

==== Container Sentinel

`IRONBARK_IN_CONTAINER`:: Baked into the container image so processes can detect they are running inside the container. Default: `false`.

==== Launcher Sentinel

`IRONBARK_LAUNCHER_INVOKED`:: Set to `true` by the generated launcher script so processes can detect Ironbark was invoked via the launcher. Default: `false`.

==== Script Variables

These variables are read by the generated launcher and zarf-bootstrap scripts:

[horizontal]
`IRONBARK_SCRIPT_CONTAINER_ENGINE`:: Container engine (`podman` or `docker`) used by scripts. Overrides the baked-in value.
`IRONBARK_SCRIPT_IMAGE`:: Container image reference used by scripts. Overrides the baked-in value.
`IRONBARK_SCRIPT_NO_INTERACTIVE`:: Set to any value to run the container without `--interactive`. Useful in CI.
`IRONBARK_SCRIPT_NO_TTY`:: Set to any value to run the container without `--tty`. Useful when piping output or in CI.
`IRONBARK_SCRIPT_VERBOSE`:: Set to any value to make scripts print verbose diagnostic output to stderr.
`IRONBARK_SCRIPT_ZARF_SOURCE_PATH`:: Override for the in-container source path used by the zarf-bootstrap script.
`IRONBARK_SCRIPT_ZARF_OUTPUT_DIR`:: Override for the host output directory used by the zarf-bootstrap script.

==== Launcher-Forwarded Variables

These variables are set by the launcher script to expose host context inside the container:

[horizontal]
`IRONBARK_HOST_DATA_DIR`:: Host directory bind-mounted into the container as `/mnt/data`.
`IRONBARK_HOST_KUBECONFIG`:: Host kubeconfig file bind-mounted at `/mnt/conf/kubeconfig`.
`IRONBARK_HOST_CONTAINER_ENGINE`:: Container engine the launcher used (e.g., `podman`).
`IRONBARK_HOST_USER`:: Username of the host user that invoked the launcher.
`IRONBARK_HOST_UID`:: Numeric UID of the host user.
`IRONBARK_HOST_GID`:: Numeric GID of the host user.
`IRONBARK_HOST_HOSTNAME`:: Hostname of the host machine.
`IRONBARK_HOST_PWD`:: Working directory the launcher was invoked from.
`IRONBARK_HOST_OS`:: Operating system of the host (output of `uname -s`).
`IRONBARK_HOST_ARCH`:: CPU architecture of the host (output of `uname -m`).
`IRONBARK_HOST_LAUNCHER_VERSION`:: Version of the Ironbark binary that generated the launcher script.
`IRONBARK_HOST_LAUNCHER_COMMIT`:: Git commit of the Ironbark binary that generated the launcher.
`IRONBARK_HOST_LAUNCHER_BUILD_TIME`:: Build timestamp of the Ironbark binary that generated the launcher.
`IRONBARK_HOST_LAUNCHER_GENERATED_AT`:: Timestamp when the launcher script was generated.
