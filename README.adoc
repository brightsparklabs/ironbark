== Overview

Ironbark is a CLI tool that bootstraps and manages Kubernetes clusters in air-gapped or disconnected environments using:

[horizontal]
https://zarf.dev/[Zarf]:: For packaging and deploying applications to air-gapped Kubernetes clusters.
https://argo-cd.readthedocs.io/[ArgoCD]:: For GitOps-based continuous deployment.
https://argo-cd.readthedocs.io/en/latest/operator-manual/cluster-bootstrapping/#app-of-apps-pattern-alternative[App of Apps Pattern]:: For managing multiple applications declaratively.
https://docs.rke2.io/[RKE2]:: (Optional) Rancher's security-focused Kubernetes distribution as an alternative to K3s.

Ironbark automates the setup of a complete GitOps workflow in disconnected environments by:

. Deploying core infrastructure components (ArgoCD, External Secrets Operator, etc.).
. Setting up internal Git and OCI registry access.
. Configuring ArgoCD to sync applications from internal repositories.
. Providing a structured way to manage application deployments.

=== Key Features

[horizontal]
Air-gapped deployment:: Works in completely disconnected environments.
Zarf integration:: Packages all dependencies for offline installation.
GitOps ready:: Automated ArgoCD setup with App of Apps pattern.
Secure by default:: Automated secret management and TLS proxy configuration.
Opinionated workflow:: Standardised deployment patterns across teams.
Multiple Kubernetes distributions:: Supports both K3s (via Zarf) and RKE2 for cluster bootstrapping.

== Quick Start

The fastest way to get started with Ironbark is to run it as a container:

[source,bash]
----
# Pull the Ironbark image.
podman pull docker.io/brightsparklabs/ironbark:latest

# Run Ironbark in API server mode (starts automatically).
podman run -d \
  --name ironbark \
  -p 8080:8080 \
  -p 3000:3000 \
  -v ~/.kube/config:/mnt/conf/kubeconfig:ro \
  docker.io/brightsparklabs/ironbark:latest

# Verify the API is running.
curl http://localhost:8080/ironbark/api/v1/health
----

The container exposes:

[horizontal]
Port 8080:: REST API for cluster management, repository operations, and configuration.
Port 3000:: Git HTTP proxy for cloning/pushing to the internal Gitea server.

See <<Usage via API>> for detailed API usage, or <<Usage via CLI>> for CLI-based operations.

== Architecture

Ironbark manages several key components:

[source]
----
┌─────────────────────────────────────────────────────────┐
│                     Kubernetes Cluster                  │
│                                                         │
│  ┌────────────┐    ┌──────────────┐   ┌──────────────┐  │
│  │   ArgoCD   │───>│  Zarf Git    │   │ Zarf OCI     │  │
│  │            │    │  Server      │   │ Registry     │  │
│  └────────────┘    └──────────────┘   └──────────────┘  │
│        │                                      ^         │
│        │ Syncs Apps                           │         │
│        v                                      │         │
│  ┌────────────────────────────────────────────┴──────┐  │
│  │  App of Apps Repo (ironbark-argocd-app-of-apps)   │  │
│  │  ├── chart/                (Helm templates)       │  │
│  │  └── values/               (App configurations)   │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
│  Deployed Applications:                                 │
│  ├── External Secrets Operator                          │
│  ├── Internal TLS Proxy                                 │
│  └── Your Applications (via App of Apps)                │
└─────────────────────────────────────────────────────────┘
----

=== Components

[horizontal]
bsl-ironbark:: Core package containing ArgoCD, External Secrets Operator, and utilities.
App of Apps Repo:: Git repository containing Helm charts and values for all applications.
Internal TLS Proxy:: Caddy-based proxy for HTTPS access to internal HTTP services.
Zarf Secrets Sync:: Ensures Zarf registry/repo credentials are available in all namespaces.

# K3s variant (default).
podman run --rm docker.io/brightsparklabs/ironbark docs

# RKE2 variant.
podman run --rm docker.io/brightsparklabs/ironbark-rke2 docs

[NOTE]

[horizontal]

`brightsparklabs/ironbark-rke2:latest`:: RKE2 variant with RKE2 installation artifacts.

=== Prerequisites

* The environment has a working Kubernetes cluster (EKS, RKE2, K3s, etc.).
* `kubectl` is configured and connected to the cluster.
* Zarf has been initialised on the cluster (`zarf init`).

If the above are not met, refer to <<Bootstrapping an Environment>>.

=== Shell Environment

The remainder of this guide assumes the following three shell variables are exported in your current session.
Set them once before working through any of the install or operational sections below; all subsequent bash snippets in this README reference them by name rather than re-stating the literal paths.

[source,bash]
----
# Base directory beneath which the per-release-environment Ironbark
# install trees live. This is the canonical brightSPARK Labs install
# root and does not normally need to change.
export IRONBARK_INSTALL_BASE_DIR="/opt/brightsparklabs/ironbark"

# Release environment this shell session targets (e.g. `production`,
# `staging`). Override per session to operate against a different
# environment without touching siblings.
export IRONBARK_RELEASE_ENVIRONMENT="production"

# Per-release-environment install directory derived from the two
# variables above. Do not override this directly - set
# `IRONBARK_INSTALL_BASE_DIR` and/or `IRONBARK_RELEASE_ENVIRONMENT`
# instead so the two stay in sync.
export IRONBARK_INSTALL_DIR="${IRONBARK_INSTALL_BASE_DIR}/${IRONBARK_RELEASE_ENVIRONMENT}"
----

=== Easy Install (recommended)

For a one-step install, use `generate installer` to emit a self-contained bash installer.
When piped through `bash`, the installer:

. Creates the per-release-environment install directory tree under `/opt/brightsparklabs/ironbark/<release-environment>/`, including the subdirectories:
.. `bin/`
.. `data/zarf/init/`
.. `data/repos/`
. Drops a versioned launcher script into `<install-dir>/bin/` and points a generic `bin/ironbark` symlink at it.
. Restores ownership of the install tree to the invoking user (`SUDO_USER` falling back to `USER`).
. If `setfacl` is available, applies recursive default ACLs on the install base directory so new files created beneath it inherit the right permissions.

[source,bash]
----
# Explicitly use registry prefix as Podman defaults to short-name resolution enforcement.
export IRONBARK_SCRIPT_IMAGE=docker.io/brightsparklabs/ironbark:<version>

# Generate the installer (targeting the release environment specified in
# `${IRONBARK_RELEASE_ENVIRONMENT}`) and pipe it through bash. `sudo` is
# required to write under `${IRONBARK_INSTALL_BASE_DIR}`; ownership of
# the tree is reverted to the invoking user automatically.
podman run --rm ${IRONBARK_SCRIPT_IMAGE} generate installer \
    --install-base-dir "${IRONBARK_INSTALL_BASE_DIR}" \
    --release-environment "${IRONBARK_RELEASE_ENVIRONMENT}" \
  | sudo bash

# Add the launcher to your $PATH (or run it directly):
export PATH="${IRONBARK_INSTALL_DIR}/bin:${PATH}"
----

Available options for `ironbark generate installer`:

[horizontal]
`--install-base-dir`:: Base directory under which the per-release-environment install directory is created. Default: `/opt/brightsparklabs/ironbark`.
`--release-environment`:: Release environment the installer targets (e.g. `production`, `staging`). Default: `production`.

All flags accepted by `ironbark generate launcher` (`--container-engine`, `--image`, `--kubeconfig`, `--no-interactive`, `--no-tty`) are also accepted by `generate installer` and are baked into the inlined launcher.

If you would rather generate and install the launcher manually, follow <<Manual Install>> below instead.

=== Manual Install

Generate a launcher script using the Ironbark container.
The launcher wraps the underlying container engine invocation so you can run `ironbark` directly:

[source,bash]
----
# Pre-create the canonical Ironbark install tree and hand ownership to the
# current user so subsequent `ironbark` invocations do not require `sudo`.
sudo mkdir -p "${IRONBARK_INSTALL_DIR}"/{bin,data/zarf/init,data/repos}
sudo chown -R "$(id -u):$(id -g)" "${IRONBARK_INSTALL_DIR}"

# If `setfacl` is available, apply recursive default ACLs on the
# per-environment install dir so any new files created beneath it
# inherit your user/group with read/write permissions, and execute
# permission for directories (and files that are already executable).
if command -v setfacl >/dev/null 2>&1; then
  sudo setfacl -R -d -m "u:$(id -un):rwX,g:$(id -gn):rwX" "${IRONBARK_INSTALL_DIR}"
  sudo setfacl -R    -m "u:$(id -un):rwX,g:$(id -gn):rwX" "${IRONBARK_INSTALL_DIR}"
fi

# Generate a launcher script (defaults to Podman) and install it onto
# your $PATH at the canonical location.
podman run --rm ${IRONBARK_SCRIPT_IMAGE} generate launcher \
  > "${IRONBARK_INSTALL_DIR}/bin/ironbark"
chmod +x "${IRONBARK_INSTALL_DIR}/bin/ironbark"

# Make sure the launcher is on your PATH for the rest of this guide. Add this
# line to your shell profile (e.g. `~/.bashrc`, `~/.zshrc`) to make it
# permanent.
export PATH="${IRONBARK_INSTALL_DIR}/bin:${PATH}"
----

Available options for `ironbark generate launcher`:

[horizontal]
`--container-engine`:: Container engine to use (`podman` or `docker`). Default: `podman`.
`--image`:: Container image reference for Ironbark. Default: `docker.io/brightsparklabs/ironbark:latest`.
`--data-dir`:: Host directory mounted into the container as the Ironbark data directory. Default: `/opt/brightsparklabs/ironbark/production/data` (the canonical install location).
`--kubeconfig`:: Host kubeconfig file mounted into the container. Default: `${HOME}/.kube/config`.
`--no-interactive`:: Bake `IRONBARK_SCRIPT_NO_INTERACTIVE` on as the default in the generated script (useful for CI). Default: `false`.
`--no-tty`:: Bake `IRONBARK_SCRIPT_NO_TTY` on as the default in the generated script (useful when piping or in CI). Default: `false`.

The generated script:

* Attempts to create the host data directory if it does not exist.
If the creation fails (e.g. permission denied) the script reports the error and exits with a non-zero status.
* Relies on `IRONBARK_IN_CONTAINER=true` being baked into the Ironbark image so code (and shell scripts) can detect that they are running inside the container, regardless of whether the launcher or a direct `podman run` was used.
* Forwards a number of useful host details into the container as `IRONBARK_HOST_*` environment variables so that Ironbark can correctly reference paths and identities on the host (e.g. when invoking nested container engines):
+
[horizontal]
`IRONBARK_HOST_USER`:: Effective host user (`${SUDO_USER:-$USER}`).
`IRONBARK_HOST_UID`:: Effective host user id (`${SUDO_UID:-$(id -u)}`).
`IRONBARK_HOST_GID`:: Effective host group id (`${SUDO_GID:-$(id -g)}`).
`IRONBARK_HOST_HOSTNAME`:: Hostname of the invoking machine.
`IRONBARK_HOST_PWD`:: Working directory the launcher was invoked from.
`IRONBARK_HOST_OS`:: Host operating system (`uname -s`).
`IRONBARK_HOST_ARCH`:: Host CPU architecture (`uname -m`).
`IRONBARK_HOST_DATA_DIR`:: Host path of the mounted data directory.
`IRONBARK_HOST_KUBECONFIG`:: Host path of the mounted kubeconfig file.
`IRONBARK_HOST_CONTAINER_ENGINE`:: Container engine used to run Ironbark (`podman` or `docker`).
`IRONBARK_HOST_LAUNCHER_VERSION`:: Version of the Ironbark binary that generated the launcher script.
`IRONBARK_HOST_LAUNCHER_COMMIT`:: Short Git commit hash of the Ironbark binary that generated the launcher script.
`IRONBARK_HOST_LAUNCHER_BUILD_TIME`:: UTC ISO 8601 timestamp recording when the Ironbark binary that generated the launcher script was built.
`IRONBARK_HOST_LAUNCHER_GENERATED_AT`:: Timestamp recording when the launcher script itself was generated.
* Honours `IRONBARK_SCRIPT_NO_INTERACTIVE` and `IRONBARK_SCRIPT_NO_TTY` at runtime: define either variable to ANY value (e.g. `true`, `1`, `yes`) to disable `--interactive` / `--tty` without regenerating the script.
Leave them unset to keep the flags enabled.
* Honours `IRONBARK_SCRIPT_VERBOSE`: define it to ANY value to print the resolved settings (container engine, image, mounts, flag state, forwarded host env vars) to stderr before invoking the container engine.

To generate a launcher targeting Docker instead of Podman (substitute `podman` for `docker` in the bootstrap command from the previous example):

[source,bash]
----
docker run --rm docker.io/brightsparklabs/ironbark generate launcher \
  --container-engine docker \
  > "${IRONBARK_INSTALL_DIR}/bin/ironbark"
chmod +x "${IRONBARK_INSTALL_DIR}/bin/ironbark"
----

=== Bootstrapping an Environment

[IMPORTANT]
--
This section applies if any of the following are true:

* The environment does not have a working Kubernetes cluster.
* Zarf has not been initialised on the cluster (`zarf init`).
--

==== Extract Bootstrap Script

When bootstrapping an fresh environment you need the `zarf` CLI and the `zarf-init-*.tar.zst` package on the host itself.
The Ironbark container ships both at `/app/resources/zarf/init`.
These can be extracted using a host-side extraction script.

[source,bash]
----
# Generate the extraction script using the launcher installed above and run
# it on the host.
ironbark generate zarf-bootstrap > extract-zarf.sh
chmod +x extract-zarf.sh
./extract-zarf.sh

# Ensure the current user can run initialise the cluster.
sudo chown -R "$(id -u):$(id -g)" "${IRONBARK_INSTALL_DIR}/data/zarf/init"
----

Available options for `ironbark generate zarf-bootstrap`:

[horizontal]
`--container-engine`, `-e`:: Container engine to use (`podman` or `docker`). Default: `podman`.
`--image`, `-i`:: Container image reference for Ironbark. Default: `docker.io/brightsparklabs/ironbark:latest`.
`--source-path`, `-s`:: Path inside the container containing the Zarf CLI and init package. Default: `/app/resources/zarf/init`.
`--output-dir`, `-o`:: Host directory which will receive the extracted Zarf assets. Default: `/opt/brightsparklabs/ironbark/production/data/zarf/init` (NOTE: This is inside the launcher's default data directory so no extra mount is required).

*The generated script:*

* Validates that the requested container engine is available on `PATH`.
* Creates the output directory if it does not already exist.
* Creates a throwaway Ironbark container, copies the Zarf assets out, then removes the throwaway container.
* Honours the following runtime overrides so you can change the defaults without regenerating the script:
.. `IRONBARK_SCRIPT_CONTAINER_ENGINE`
.. `IRONBARK_SCRIPT_IMAGE`
.. `IRONBARK_SCRIPT_ZARF_SOURCE_PATH`
.. `IRONBARK_SCRIPT_ZARF_OUTPUT_DIR`
.. `IRONBARK_SCRIPT_VERBOSE`
* Does NOT run `zarf init` itself; the operator retains explicit control over the bootstrap step.

[IMPORTANT]
--
Before emitting the script, `generate zarf-bootstrap` verifies that the Zarf assets (the `zarf` CLI and a matching `zarf-init-*.tar.zst` package) actually exist at the configured source path.
This catches misconfigurations such as a stale image or a wrong `--source-path` early, instead of letting the operator discover the problem after running the resulting script on the host.
--

==== Bootstrap an Existing Cluster

[NOTE]
--
This section applies when the following are true:

. The environment has a working Kubernetes cluster (EKS, K3s, etc.).
. `kubectl` is configured and connected to the cluster.
. Zarf has not been initialised on the cluster (`zarf init`).
--

Bootstrap the environment by running the script:

[source,bash]
----
# Bootstrap the host (installs the Zarf in-cluster components).
cd "${IRONBARK_INSTALL_DIR}/data/zarf/init"
./zarf init --components=git-server --confirm
----

==== Bootstrap a New Cluster

[NOTE]
--
This section applies when the following are true:

. A new Kubernetes cluster should be created.
--

IMPORTANT: If `fapolicyd` is running ensure the correct rules have been generated as per <<Generating fapolicyd Rules>>.

Bootstrap the environment by running the script:

[source,bash]
----
# NOTE: Must be run as root (not sudo) in order to install K3s.
sudo -i

# Bootstrap the host (installs K3s and the Zarf in-cluster components).
cd "${IRONBARK_INSTALL_DIR}/data/zarf/init"
./zarf init --components k3s,git-server --confirm
----

==== Bootstrap with RKE2 (Alternative to K3s)

[NOTE]
--
This section applies when you want to use RKE2 instead of K3s for the Kubernetes cluster.
RKE2 is Rancher's next-generation Kubernetes distribution focused on security and compliance.
--

Ironbark provides an RKE2 variant container image (`brightsparklabs/ironbark-rke2:latest`) that includes all necessary RKE2 installation artifacts for air-gapped deployment.

===== Extract RKE2 Artifacts

First, extract the RKE2 installation files from the RKE2 variant container:

[source,bash]
----
# Generate the RKE2 extraction script using the RKE2 variant image.
# Must use ironbark-rke2 image, not the default ironbark image.
docker run --rm docker.io/brightsparklabs/ironbark-rke2:latest \
  generate rke2-bootstrap > extract-rke2.sh
chmod +x extract-rke2.sh
./extract-rke2.sh

# Ensure the current user can access the extracted files.
sudo chown -R "$(id -u):$(id -g)" "${IRONBARK_INSTALL_DIR}/data/rke2"
----

Available options for `ironbark generate rke2-bootstrap`:

[horizontal]
`--container-engine`, `-e`:: Container engine to use (`podman` or `docker`). Default: `podman`.
`--image`, `-i`:: Container image reference for Ironbark RKE2 variant. Default: `docker.io/brightsparklabs/ironbark-rke2:latest`.
`--source-path`, `-s`:: Path inside the container containing the RKE2 installation artifacts. Default: `/app/resources/rke2`.
`--output-dir`, `-o`:: Host directory which will receive the extracted RKE2 assets. Default: `/opt/brightsparklabs/ironbark/production/data/rke2`.

*The generated script:*

* Validates that the requested container engine is available on `PATH`.
* Creates the output directory if it does not already exist.
* Creates a throwaway Ironbark container, copies the RKE2 assets out, then removes the throwaway container.
* Honours the following runtime overrides so you can change the defaults without regenerating the script:
.. `IRONBARK_SCRIPT_CONTAINER_ENGINE`
.. `IRONBARK_SCRIPT_IMAGE`
.. `IRONBARK_SCRIPT_RKE2_SOURCE_PATH`
.. `IRONBARK_SCRIPT_RKE2_OUTPUT_DIR`
.. `IRONBARK_SCRIPT_VERBOSE`
* Does NOT run the RKE2 installation itself; the operator retains explicit control over the installation step.

The extraction script downloads the following artifacts:

* `install.sh` - RKE2 installation script
* `rke2.linux-amd64.tar.gz` - RKE2 binaries
* `rke2-images-cilium.linux-amd64.tar.zst` - Container images with Cilium CNI
* `sha256sum-amd64.txt` - Checksums for verification
* `VERSION.json` - RKE2 version information

[IMPORTANT]
--
The extracted artifacts include Cilium container images.
To use Cilium, you must add `cni: cilium` to `/etc/rancher/rke2/config.yaml` (see configuration step below).
Without this setting, RKE2 will default to Canal (Calico + Flannel) and the Cilium images will not be used.
--

===== Install RKE2

After extracting the artifacts, install RKE2 in air-gapped mode:

[source,bash]
----
cd "${IRONBARK_INSTALL_DIR}/data/rke2"

# Install RKE2 using the extracted artifacts (air-gapped installation).
sudo INSTALL_RKE2_ARTIFACT_PATH="${IRONBARK_INSTALL_DIR}/data/rke2" ./install.sh
----

===== Configure RKE2

Create the RKE2 configuration file with Cilium CNI.
The extracted artifacts include a template configuration file:

[source,bash]
----
# Copy the template configuration to the RKE2 config directory.
sudo mkdir -p /etc/rancher/rke2
sudo cp /tmp/rke2-cilium/config.yaml.template /etc/rancher/rke2/config.yaml

# Review and modify the configuration as needed.
sudo vi /etc/rancher/rke2/config.yaml
----

The template configuration includes:

[source,yaml]
----
# RKE2 server configuration
# See: https://docs.rke2.io/install/configuration

# Use Cilium as the CNI (Container Network Interface).
# Cilium provides eBPF-based networking, security, and observability.
cni: cilium

# Make kubeconfig readable by non-root users.
write-kubeconfig-mode: "0644"

# Additional TLS SANs for API server certificate.
# Add any additional hostnames or IPs that clients will use to access the API server.
tls-san:
  - localhost
  - 127.0.0.1
  # - your-hostname.example.com
  # - 192.168.1.100
----

[NOTE]
--
The `cni: cilium` configuration is required to use Cilium.
Without this setting, RKE2 defaults to Canal (Calico + Flannel).
The extracted RKE2 artifacts include Cilium container images (`rke2-images-cilium.linux-amd64.tar.zst`).
--

===== Start RKE2

Enable and start the RKE2 service:

[source,bash]
----
# For server node (control plane).
sudo systemctl enable rke2-server.service
sudo systemctl start rke2-server.service

# Wait for RKE2 to be ready (may take 1-2 minutes).
sudo systemctl status rke2-server.service

# Configure kubectl to use the RKE2 cluster.
export KUBECONFIG=/etc/rancher/rke2/rke2.yaml
/var/lib/rancher/rke2/bin/kubectl get nodes
----

[NOTE]
--
On a single-node cluster, you may see one Cilium operator pod in `Pending` status.
This is normal and expected behaviour.

The Cilium operator deployment is configured for 2 replicas (high availability), but both replicas try to bind to the same host ports.
On a single-node cluster, only one replica can bind to those ports, so the second remains pending.

Check the status:
[source,bash]
----
/var/lib/rancher/rke2/bin/kubectl get deployment -n kube-system cilium-operator
----

You should see `READY 1/2`, which means 1 of 2 desired replicas is running.
This is sufficient for full Cilium operation.
The second replica will automatically schedule when you add a second node to the cluster.
--

===== Adding Additional Nodes

RKE2 supports two types of nodes:

[horizontal]
Server nodes:: Control plane + etcd + worker (recommended for small deployments, provides HA for control plane)
Agent nodes:: Worker only (for larger deployments where you want dedicated control plane nodes)

====== Adding Server Nodes (Control Plane + Worker)

For small deployments, adding additional server nodes provides high availability for the control plane while also serving as workers.

*On the first server node:*

[source,bash]
----
# Get the server token (required for additional server nodes to join).
sudo cat /var/lib/rancher/rke2/server/token
----

*On each additional server node:*

[source,bash]
----
# Extract and install RKE2 using the same process as the first server node.
# (Use the same ironbark-rke2 image and bootstrap script)

# Create server configuration.
sudo mkdir -p /etc/rancher/rke2
sudo tee /etc/rancher/rke2/config.yaml > /dev/null <<EOF
# RKE2 server configuration (joining existing cluster)
server: https://<FIRST_SERVER_IP>:9345
token: <SERVER_TOKEN>

# Use Cilium as the CNI
cni: cilium

# Make kubeconfig readable by non-root users
write-kubeconfig-mode: "0644"

# Additional TLS SANs for API server certificate
tls-san:
  - localhost
  - 127.0.0.1
EOF

# Stage the RKE2 images.
cd /path/to/rke2-artifacts
sudo mkdir -p /var/lib/rancher/rke2/agent/images/
sudo cp rke2-images-cilium.linux-amd64.tar.zst /var/lib/rancher/rke2/agent/images/

# Start the RKE2 server service.
sudo systemctl enable rke2-server.service
sudo systemctl start rke2-server.service
----

Replace `<FIRST_SERVER_IP>` with the IP address of your first server node and `<SERVER_TOKEN>` with the token from `/var/lib/rancher/rke2/server/token`.

[IMPORTANT]
--
For production high availability, you should have an odd number of server nodes (3 or 5 recommended) to maintain etcd quorum.
--

====== Adding Agent Nodes (Worker Only)

For larger deployments where you want dedicated control plane nodes.

*On any server node:*

[source,bash]
----
# Get the node token (required for agent nodes to join).
sudo cat /var/lib/rancher/rke2/server/node-token
----

*On each agent node:*

[source,bash]
----
# Extract and install RKE2 using the same process as the server node.
# (Use the same ironbark-rke2 image and bootstrap script)

# Create agent configuration.
sudo mkdir -p /etc/rancher/rke2
sudo tee /etc/rancher/rke2/config.yaml > /dev/null <<EOF
# RKE2 agent configuration
server: https://<SERVER_IP>:9345
token: <NODE_TOKEN>
EOF

# Stage the RKE2 images.
cd /path/to/rke2-artifacts
sudo mkdir -p /var/lib/rancher/rke2/agent/images/
sudo cp rke2-images-cilium.linux-amd64.tar.zst /var/lib/rancher/rke2/agent/images/

# Start the RKE2 agent service.
sudo systemctl enable rke2-agent.service
sudo systemctl start rke2-agent.service
----

Replace `<SERVER_IP>` with the IP address of any server node and `<NODE_TOKEN>` with the token from `/var/lib/rancher/rke2/server/node-token`.

====== Verifying Node Addition

Once nodes join, verify on any server node:

[source,bash]
----
/var/lib/rancher/rke2/bin/kubectl get nodes
----

==== Generating fapolicyd Rules

Hosts that enforce `fapolicyd` need explicit rules to allow execution of the binaries Ironbark relies on (the extracted `zarf` CLI and the installed `k3s` CLI).
Generate a matching rules file with:

[source,bash]
----
# Defaults assume `/opt/brightsparklabs/ironbark/production/data/zarf/init/zarf` and
# `/usr/local/bin/k3s`.
ironbark generate fapolicy-rules \
  --zarf-path "${IRONBARK_INSTALL_DIR}/data/zarf/init/zarf" \
  --k3s-path /usr/local/bin/k3s \
  | sudo tee /etc/fapolicyd/rules.d/00-ironbark.rules
sudo systemctl restart fapolicyd
----

Available options for `ironbark generate fapolicy-rules`:

[horizontal]
`--zarf-path`:: Absolute host path of the extracted Zarf CLI. Default: `/opt/brightsparklabs/ironbark/production/data/zarf/init/zarf` (matches the default `--output-dir` of `generate zarf-bootstrap`).
`--k3s-path`:: Absolute host path of the installed K3s CLI. Default: `/usr/local/bin/k3s`.

The generated rules file allows execution and reading of each supplied binary.

=== Invoking Bundled Tools

The Ironbark container image bundles a number of CLI tools under `/app/bin/` so they are available on disconnected/airgapped hosts without separate installation.
Invoke them via `ironbark exec`:

[source,bash]
----
# List the available tools (auto-discovered at runtime; a shell
# binary is also auto-registered if the image ships one).
ironbark exec --help

# Forward all remaining args verbatim to the underlying tool.
ironbark exec <tool> [args...]

# Drop into an interactive shell inside the container - useful for
# one-off troubleshooting or ad-hoc commands that are not exposed
# elsewhere. The exact subcommand name depends on what the image
# ships (run `ironbark exec --help` to see).
ironbark exec <shell>
----

Signal handling, exit codes and stdio behave exactly as if you had invoked the tool directly: under the hood `ironbark exec` `execve`'s into the requested binary.

The remaining sections of this guide use tool names directly (e.g. `kubectl`, `zarf`).
On hosts where those tools are not installed locally, replace each invocation with `ironbark exec <tool>` to use the version bundled in the image.

== Diagnostic Commands

Ironbark groups its troubleshooting subcommands under `ironbark debug`.
These commands never modify any external system; they only read and print information that Ironbark already has access to.

=== Inspecting Settings

`ironbark debug settings` prints the full catalogue of `IRONBARK_*` environment variables Ironbark knows about, along with each variable's current effective value, declared default, source (env or default), scope, and a short description.

[source,bash]
----
# Default human-readable table.
ironbark debug settings

# Machine-readable output for piping into other tools.
ironbark debug settings --format json
ironbark debug settings --format yaml
----

The catalogue in `src/internal/settings/settings.go` is the single source of truth for every `IRONBARK_*` variable understood by the system.
The unit tests for that package enforce that variable names are unique, well-formed (`IRONBARK_*` prefix), and that every Go-consumed accessor has a matching catalogue entry, so the output of `debug settings` cannot drift from the real list of variables Ironbark reads.

Variables marked sensitive (currently none) are rendered with their values redacted as `<redacted>` regardless of the chosen output format.

== Adding New Applications

To add a new application to your Ironbark deployment:

. Ensure the Helm chart is mirrored to the Zarf OCI registry (via a Zarf package).
+
Any chart declared under `components[].charts` in a mirror package is pushed to the in-cluster OCI registry automatically when `ironbark init packages` runs.
The chart lands at a predictable path that preserves upstream provenance:
+
URL-sourced charts (`oci://` or `https://`):: `oci://<zarf-registry>/ironbark/charts/<upstream-host-and-path>/<chart-name>:<chart-version>`.
+
E.g.
+
* A chart declared as:
+
----
url: oci://ghcr.io/cowboysysop/charts/whoami (version `6.0.0`)
----
* Lands at:
+
----
oci://<zarf-registry>/ironbark/charts/ghcr.io/cowboysysop/charts/whoami:6.0.0
----
Local charts (`localPath`, `gitPath`):: `oci://<zarf-registry>/ironbark/charts/<zarf-package-name>/<chart-name>:<chart-version>`.
+
The Zarf package name is used as the namespace because no upstream URL is available; this prevents collisions when two packages ship a chart with the same name.
+
All four Zarf chart source types are supported (`localPath`, `gitPath`, `url: https://`, `url: oci://`).
Use the predictable path to reference the mirrored chart from your ArgoCD `Application` (or any other in-cluster consumer).
+
[NOTE]
.Umbrella (chart-of-charts) support
--
Umbrella charts work without any special configuration.
`zarf package create` vendors all `Chart.yaml` dependencies into the parent chart's `charts/` directory at package-build time, so by the time the chart reaches Ironbark's mirror step it is a self-contained archive.
Only the umbrella chart itself is pushed to the in-cluster registry; sub-charts ride along inside it and Helm resolves them locally at install time.

Caveat: container images referenced from sub-chart templates or hooks are not always auto-detected by Zarf's image discovery pass.
If a sub-chart fails to deploy because an image was not mirrored, add the missing image to the parent component's `images:` list in `zarf.yaml`.
--
+
[NOTE]
--
This works around an upstream Zarf limitation where `zarf package mirror-resources` only mirrors images and Git repos, never Helm charts.
The chart-mirror step is implemented in Ironbark itself; see `src/internal/zarf/charts.go`.
--

. Edit the App of Apps configuration:
+
[source,bash]
----
cd "${IRONBARK_HOST_DATA_DIR}/repos/ironbark-argocd-app-of-apps"
----

. Add the application to `chart/values.yaml`:
+
The `chart.name` must be the chart path mirrored by Ironbark, without the `oci://<zarf-registry>/` prefix (ArgoCD prepends the registry host from the repo secret).
+
For example, the canary chart at:
+
----
oci://<zarf-registry>/ironbark/charts/ghcr.io/cowboysysop/charts/whoami:6.0.0
----
+
Is referenced as:
+
[source,yaml]
----
applications:
  - name: whoami
    chart:
      name: ironbark/charts/ghcr.io/cowboysysop/charts/whoami
      targetRevision: 6.0.0
    values:
      path: values/whoami/values.yaml
      targetRevision: HEAD
      # Optional: Set Helm values from file contents (equivalent to `helm --set-file`).
      fileParameters:
        # Equivalent to `helm --set-file config.json=values/whoami/config.json`.
        - name: config.json
          path: values/whoami/config.json
        # Equivalent to `helm --set-file tls.cert=values/whoami/cert.pem`.
        - name: tls.cert
          path: values/whoami/cert.pem
----

. Create values file at `values/whoami/values.yaml`:
+
[source,yaml]
----
# Your Helm values here.
replicaCount: 2
----

. Commit and push changes:
+
[source,bash]
----
git add .
git commit -m "Add whoami"
ironbark repo push
----

. ArgoCD will automatically deploy the application.
